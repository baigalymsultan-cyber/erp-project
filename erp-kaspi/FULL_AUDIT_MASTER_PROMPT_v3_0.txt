Основа аудита: файл «Prompt .txt» из Library, 2 927 строк.
Аудит проведён по всем §0–§135; для каждого раздела указан диапазон строк.

ВАЖНО: это аудит самого MASTER PROMPT v3.0, а не аудит текущего кода проекта.
Утверждение «IMPLEMENTED» в существующей Requirements Matrix не принимается
как доказательство корректности требования: здесь проверяется именно формулировка.

СТАТУСЫ:
P0 = критическая дыра; исправить до production/до соответствующего домена.
P1 = важное усиление; желательно закрыть до production.
P2 = улучшение/операционная зрелость.
OK = требование в основном корректно, но может быть уточнено.

ОФИЦИАЛЬНАЯ ПРОВЕРКА:
1) Kaspi Guide: актуальные материалы 2026 года по комиссиям, доставке и API.
2) КГД/официальная база РК: налоговые и ЭСФ-изменения 2026 года.
3) PostgreSQL official documentation: RLS, constraints, partitioning.
4) Alembic official documentation: autogenerate требует ручной проверки.
5) OWASP ASVS 5.0 и OWASP API Security Top 10: authorization/security verification.

КЛЮЧЕВОЙ ВЫВОД:
MASTER PROMPT v3.0 имеет сильный engineering-control слой, но недостаточно
строго разделяет operational accounting, double-entry accounting, tax/fiscal
compliance, external API contracts и immutable financial correction flows.
Ниже исправления сформулированы так, чтобы не переписывать проект с нуля.

КЛЮЧЕВОЕ ИСПРАВЛЕНИЕ КОНФЛИКТА АВТОНОМНОСТИ
==============================================================================
Было: «не переходить к следующему шагу без команды пользователя».
Одновременно: «autonomous project planning» и автономная работа.
Исправить на три режима:
A) Technical execution — автономно.
B) Architecture decision — автономно через ADR, если обратимо и не меняет business semantics.
C) Protected decision — STOP/BLOCKED: налог, право, бухгалтерская семантика,
   финансовые проводки, возвраты, Kaspi contract, payroll legal treatment.
Это позволяет агенту не зависать на каждом шаге, но исключает опасные выдуманные правила.

==============================================================================
КЛЮЧЕВОЕ ИСПРАВЛЕНИЕ KASPI
==============================================================================
Kaspi-правила должны быть versioned. Официальные материалы 2026 года показывают,
что условия меняются: комиссия с 5 января 2026 года учитывает НДС отдельно,
а тарифы доставки с 1 января 2026 года зависят от суммы заказа, направления и веса.
Следовательно, тариф нельзя считать вечной константой в Python.
Нужно хранить source/effective_from/effective_to и применять историческое правило.

==============================================================================
КЛЮЧЕВОЕ ИСПРАВЛЕНИЕ ALEMBIC
==============================================================================
Autogenerate нельзя считать источником истины. Официальная документация Alembic
прямо указывает, что autogenerate не идеален и сгенерированные миграции нужно
вручную просматривать и корректировать. Поэтому Quality Gate должен требовать
manual review + upgrade + downgrade/restore strategy + schema diff.

==============================================================================
КЛЮЧЕВОЕ ИСПРАВЛЕНИЕ RLS / AUTHORIZATION
==============================================================================
PostgreSQL RLS предоставляет default-deny поведение при включённой RLS без
подходящей policy, но владелец таблицы обычно не подчиняется RLS. Поэтому
нельзя считать одной RLS достаточно: нужны DB roles/least privilege + application
authorization + object/IP scope + тесты обхода.
