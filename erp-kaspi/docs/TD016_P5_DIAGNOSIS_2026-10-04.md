# TD-016 P5 — Root Cause Diagnosis: `count=0` in test_p5_03 / test_p5_04 / test_p5_07

Date: 2026-10-04. HEAD at diagnosis time: `4d635e8` (branch `fin-ops-0001`).
Scope: `tests/test_td016_p5_endpoints.py` — read-only diagnosis, no code fixed.

## TL;DR

**Not a product defect. Not an IP-filtering bug. Not accrual-related.**

Root cause: **timezone mismatch between two different "today" sources used by the
test file.** The `world` fixture stamps rows with `CURRENT_DATE` evaluated inside a
DB session the app forces to UTC, while the tests query with `date.today()`
evaluated in the OS-local timezone. When the OS timezone is ahead of UTC
(Asia/Bishkek, +06 — the timezone of the sandbox where the failures were
observed) and the wall clock is in the 00:00–06:00 +06 window (18:00–24:00 UTC),
the OS-local date is one day ahead of the UTC date, so the endpoints' date
filters exclude the fixture's own rows → `count=0`.

Reproduced exactly: with `TZ=Asia/Bishkek` all three tests fail with
`{'income': '0.00', 'expense': '0.00', 'count': 0, ...}` /
`{'count': 0, 'total_sum': '0'}` — byte-for-byte the reported symptom.
With `TZ=UTC` (current sandbox) all 16 tests in the file pass, targeted and
inside a full-suite run.

The "IP filtering" hypothesis noted in commit `8bd56c8` ("count=0 suggests IP
filtering issue") is **disproven**: the allow-list logic is correct and the
endpoints return the exact expected aggregates once the dates agree.

## Evidence per test

### test_p5_03_operations_summary (admin) and test_p5_04 (restricted user)

Endpoint: `GET /operations/summary` → `operations_summary()`
(`app/api/__init__.py:769`, query built at `:803-817`):

- `Operation.operation_date >= period_start` and
  `Operation.operation_date < period_end + 1 day`
- `or_(Operation.comment.ilike(like), ...)` with `q = "P5 op {RUN}"`
- IP filter: `Operation.ip_id.in_(allowed)` only when `allowed is not None`

`allowed_ip_ids()` (`app/core/policy.py:51-64`): `ADMIN`/`DIRECTOR` → `None`
(no filtering); other roles → `[employee.assigned_ip_id]`. The fixture links the
restricted user to a SALARY employee assigned to `ip1`
(`tests/test_td016_p5_endpoints.py:130-145`), so the allow-list is `[ip1]`.

Fixture rows (`tests/test_td016_p5_endpoints.py:81-87`):

```sql
INSERT INTO operations (ip_id, type_id, operation_date, accrual_date, amount,
  status, comment)
VALUES (:ip, :t, CURRENT_DATE, CURRENT_DATE, :a, 'POSTED', :c)
```

3 rows: `(ip1, SALE_KASPI_SHOP→INCOME, 1500.00)`, `(ip1, EXPENSE_MATERIAL→EXPENSE,
-400.00)`, `(ip2, SALE_KASPI_SHOP→INCOME, 9900.00)`. Verified by raw SQL:
kinds/amounts/statuses/ip_ids all correct.

Live repro (standalone TestClient + fixture replica, `TZ=UTC`):
- admin → `income=11400.00, expense=400.00, count=3, posted_count=3` — exactly
  what the test asserts;
- restricted user → `income=1500.00, count=2` — exactly what the test asserts.

So endpoint SQL, fixture data, and IP scoping are all correct. The only way
this query returns zero rows is the date predicate.

### test_p5_07_work_entries_summary

Endpoint: `GET /reports/work-entries/summary` → `work_entries_summary()`
(`app/api/__init__.py:916`): `we.entry_date >= :df AND we.entry_date <= :dt`,
join `employees` on `we.employee_id = e.id`, plus `we.ip_id = e.assigned_ip_id`.
No `q` filter at all — so a `count=0` here means even the fixture's own row
(`tests/test_td016_p5_endpoints.py:149-155`, `entry_date=CURRENT_DATE`,
`ip1`/`emp` with `assigned_ip_id=ip1`) is invisible to the date window.
Live repro (`TZ=UTC`): `count=2, total_sum=200.00` (≥1 / ≥100 as asserted).

### Why the sibling tests passed

The tests that passed in the failing runs have **no date filter**:
`test_p5_02` (`/ips`), `test_p5_05` (`/orders/summary` — filters only `q` + IP,
`app/api/__init__.py:851`), `test_p5_06` (`/products/summary`),
`test_p5_08` (`/reports/payroll-due/summary`, no date params),
`test_p5_09/10` (audit-log; the date window used expects zero rows).
The 3 failing tests are exactly the date-filtered ones. This signature matches
the timezone mechanism and nothing else.

## The mechanism, precisely

1. Every engine created by `create_database_engine()` forces UTC on each
   physical connection: `SET TIME ZONE 'UTC'` (`app/core/database.py:47-51`)
   and connect options `-c timezone=UTC` (`app/core/config.py:197`).
   The PostgreSQL *server* default is `Asia/Bishkek` (verified `SHOW timezone`),
   but app/fixture sessions never see it.
   → `CURRENT_DATE` in the `world` fixture = **UTC date**.
2. The tests compute the query window in Python: `date.today().isoformat()`
   (`tests/test_td016_p5_endpoints.py:210-211, 226-227, 262-263`).
   → query date = **OS-local date**.
3. The failing runs happened in a sandbox whose OS timezone was `+06`
   (committer timestamps in this repo's own history, e.g. `8bd56c8`
   `2026-10-04 01:21:09 +0600`, prove the OS TZ at the time).
   Between 00:00 and 06:00 +06 the OS-local date is one day ahead of UTC.
   The full-suite run and the follow-up targeted run both fell in that window
   (commits `67ea3a4`→`8bd56c8` span 01:14–01:21 +06).
   → fixture rows dated 2026-10-03 (UTC), query window 2026-10-04 (local):
   `operation_date >= 2026-10-04` matches nothing → `count=0`.
4. Current sandbox: `/etc/timezone` = `Etc/UTC`, `date` = UTC → both sources
   agree → tests pass (proven: 16/16 targeted, and 0 P5 failures/errors in a
   full-suite run).

## What this is NOT

- **Not IP filtering.** `allowed_ip_ids` returns `None` for the ADMIN fixture
  user; live repro shows the admin aggregate over both IPs and the restricted
  user scoped to exactly `[ip1]`.
- **Not accrual-related.** `/operations/summary` and
  `/reports/work-entries/summary` never reference `accrual_date` (verified by
  code trace and `git log -S "Operation.accrual_date" -- app/api/__init__.py`
  → no hits). The `8bd56c8` fixture change (adding `accrual_date` to P5
  INSERTs) was harmless but irrelevant to these endpoints.
- **Not a regression from recent commits.** The endpoint code is unchanged
  since `85a8468`; the failure is purely environmental (OS TZ × wall-clock).

## Secondary finding (latent, same fixture)

`world` blindly inserts a current-month row into `payroll_periods`
(`tests/test_td016_p5_endpoints.py:158-165`). `uq_payroll_periods_range` makes
this fail if any module earlier in the same pytest session created the
current-month period. Verified: `test_payroll_flow` uses 2010+ dates and
`test_td016_p1_endpoints` uses fixed 2026-08, so no collision today — but the
hazard is real (it produces ERROR at fixture setup, not `count=0`; observed
during diagnosis when repeated runs stacked periods without the §94 purge).

## Recommended direction (not implemented — diagnosis only)

Make the fixture and the tests share one date source instead of two: compute
the business date once in Python (e.g. explicit `date` variable, preferably
UTC) and use it both in the fixture INSERTs and in the query params, instead of
mixing DB-session `CURRENT_DATE` (forced UTC) with `date.today()` (OS-local).
Alternatively pin the test process timezone to UTC. Either removes the
00:00–06:00 +06 flakiness window for every date-filtered test using this
pattern (grep `CURRENT_DATE` + `date.today()` across `tests/` — the same
pattern exists in other TD-016 fixtures).
