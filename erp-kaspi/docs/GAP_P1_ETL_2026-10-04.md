### F-ETL-004: No chunk_size validation
**Severity:** P2 (Medium)
**File:** `etl/import_excel.py:422-427` (argparse), `etl/import_excel.py:353` (range)
**Evidence:**
```python
parser.add_argument("--chunk-size", type=int, default=None, ...)
# ...
for chunk_start in range(0, len(rows), chunk_size):  # ValueError if 0!
```
No validation. `--chunk-size 0` → `ValueError: range() arg 3 must not be zero`. `--chunk-size -5` → infinite loop or empty chunks.
**Impact:** Confusing error messages. Potential hang with negative values.
**Proposed fix:** Add validation in `main()`:
```python
if args.chunk_size is not None and args.chunk_size <= 0:
    print("ERROR: --chunk-size must be positive", file=sys.stderr)
    return 2
```
Also validate in `run_import()` for API callers.
**Tests required:** Test with 0, negative, and valid chunk_size.
**Owner decision:** NO.

### F-ETL-005: Excel imports don't store raw payload
**Severity:** P2 (Medium)
**File:** `etl/import_excel.py` (entire file — no raw payload storage)
**Evidence:** `import_batches` has `source_name` (filename only), `error_details` (capped at 50). No table stores the actual Excel file content or row data. `raw_kaspi_payloads` exists but is Kaspi-specific.
**Impact:** Cannot audit what was actually imported. If source file is lost, no way to reconstruct. Error investigation limited to 50 errors.
**Proposed fix:** Options:
- A: Store file hash + row count in `import_batches` (lightweight)
- B: Store full file in new `raw_import_payloads` table (heavyweight)
- C: Store failed rows' raw data in `error_details` (targeted)
Recommend A+C: hash for integrity, full raw data for failed rows.
**Tests required:** Hash verification, error row raw data preservation.
**Owner decision:** NO — technical choice, recommend A+C.

### F-ETL-007: Error details capped at 50, raw row data incomplete
**Severity:** P3 (Low)
**File:** `etl/import_excel.py:382`
**Evidence:** `batch.error_details = {"errors": errors[:50]}  # cap the JSONB payload`
Error entries contain `{"row": str(index), "error": "..."}` — row number and error message, but NOT the raw row data that caused the error.
**Impact:** Debugging import errors requires the original file. With 50+ errors, information is lost.
**Proposed fix:** Include raw row dict in error entries (first 50). Or store all errors in a separate table.
**Tests required:** Verify error entries contain raw row data.
**Owner decision:** NO.

### F-ETL-008: Concurrent import race condition
**Severity:** P1 (High)
**File:** `etl/import_excel.py:255-265` (pre-check), `etl/import_excel.py:305` (insert)
**Evidence:** Fingerprint pre-check is done in batches, then rows are inserted. Between pre-check and insert, another process could insert the same fingerprint. The unique index `uq_operations_import_fingerprint` will catch it, but:
- No `IntegrityError` handling — generic `except Exception` catches it
- In chunked mode, the entire chunk rolls back on a single duplicate
- Error message is confusing (not "duplicate", just IntegrityError)
**Impact:** Concurrent imports of the same file can cause chunk rollbacks and confusing errors. Not data corruption (unique index protects), but poor UX and wasted work.
**Proposed fix:** Catch `IntegrityError` specifically, treat as duplicate (increment duplicates counter, continue). Or use `ON CONFLICT DO NOTHING` for inserts.
**Tests required:** Concurrent import test with two processes, verify zero duplicates and clear status.
**Owner decision:** NO — technical fix.

### F-ETL-009: KaspiPayoutItem has no creation path

**Impact:** Cannot record payout breakdown via API. Reconciliation (`reconcile_payout`) requires items to exist.
**Proposed fix:** Add `POST /kaspi/payouts/{id}/items` endpoint with idempotency (unique on payout_id + order_id if applicable).
**Tests required:** Item creation, duplicate prevention, reconciliation with items.
**Owner decision:** NO.

### F-ETL-010: POST /kaspi/payouts duplicate handling
**Severity:** P2 (Medium)
**File:** `app/api/__init__.py:1716-1739`
**Evidence:**
```python
payout = KaspiPayout(...)
session.add(payout)
session.flush()  # IntegrityError if duplicate (ip_id, external_payout_id)!
return {"id": payout.id, "status": payout.status}
```
Unique constraint `uq_kaspi_payouts_external` exists (schema.sql:1443), but no pre-check or graceful handling. Duplicate → 500 Internal Server Error.
**Impact:** Poor API UX. Clients can't distinguish "already exists" from server error.
**Proposed fix:** Check for existing payout by `(ip_id, external_payout_id)` before insert. Return 200 with existing ID (idempotent) or 409 Conflict.
**Tests required:** Duplicate payout POST returns idempotent success, not 500.
**Owner decision:** NO — recommend idempotent 200 (standard for payout registration).
