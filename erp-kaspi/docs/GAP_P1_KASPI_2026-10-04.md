## What exists today

- **Schema:** `kaspi_api_credentials` (AES-256-GCM token vault), `raw_kaspi_payloads`
  (SHA-256 dedup), `sync_log`, `kaspi_payouts` (+`uq_kaspi_payouts_external`),
  `kaspi_payout_items` (8 match statuses), `v_kaspi_reconciliation` view.
- **Client skeletons:** `KaspiShopClient` / `KaspiPayClient` (`BaseKaspiClient.run_sync`)
  — transport-abstracted, raw-payload storing, sync_log lifecycle. **No endpoint
  paths wired** (correctly frozen per OQ-003).
- **Services:** `reconcile_payout()` (tolerance check), `reconcile_payout_full()`
  (8-class line classifier: MATCHED/DUPLICATE/MISSING_ORDER/AMOUNT_MISMATCH/
  COMMISSION_MISMATCH/DELIVERY_MISMATCH/PARTIAL/UNEXPLAINED).
- **API:** `GET /kaspi/payouts`, `POST /kaspi/payouts` (manual envelope),
  `GET /reports/kaspi-reconciliation`, `GET /kaspi/sync-log`.
- **ETL:** Kaspi Excel rows (`"Продажа"` → `SALE_KASPI_PAY`, `"Комиссия"` →
  `EXPENSE_KASPI_FEE`) go through the generic fingerprint-idempotent import —
  re-import safe (proven by P0-2 tests).

## Findings

### KASPI-001 — No Shop API order-import adapter (P1, HIGH)

- **Evidence:** `KaspiShopClient` is never instantiated outside
  `app/integrations/kaspi/` (grep: zero usages in `app/services`, `app/api`,
  `etl`). Orders enter only via manual `POST /orders` with `external_order_id`.
- **What's VERIFIED and usable:** `GET /v2/orders` + pagination + order field list
  (q3201). `uq_orders_ip_external (ip_id, external_order_id)` already gives the
  idempotency key for upsert.
- **Missing:** request builder (page/filter → wire params), JSON:API response
  mapper (only VERIFIED fields: `code`, `totalPrice`, `paymentMode`, `status`,
  `state`, `creationDate`, …), order upsert service, sync scheduler/trigger.
- **Proposed (no invented contract):** `ShopOrderAdapter(BaseKaspiClient)` that
  implements ONLY the q3201 surface: `GET {base}/orders?page[number]&page[size]
  &filter[orders][state]&filter[orders][creationDate][$ge|$le]`, maps VERIFIED
  fields to `orders` rows keyed by `code` → `external_order_id`. Statuses map to
  internal order statuses via an explicit, configurable table (not guessed).
  Entries mapping stays out until `orderentries` fields are officially confirmed.
- **Tests required:** mapper unit tests with fixture payloads shaped exactly like
  q3201 examples; upsert idempotency test (same `code` twice → one order);
  pagination walk test (mock transport).
- **OWNER decision:** OQ-KASPI-001 — provide a real Seller API `X-Auth-Token`
  (generated by the company head in the seller cabinet) and confirm the target
  ИП mapping. Without a token the adapter ships code-complete but dormant.
  System can build everything else without the owner.

### KASPI-002 — Payout items have no writer; reconciliation flow is dead (P1, HIGH)

- **Evidence:** `KaspiPayoutItem(` is instantiated **nowhere** in `app/` (only
  `tests/test_reconciliation.py`). No API endpoint creates payout items.
  `kaspi_payouts.operation_id` (payout → financial operation link) is never
  set by any code path. Consequence: `reconcile_payout_full()`,
  `v_kaspi_reconciliation`, and `GET /reports/kaspi-reconciliation` always
  operate on empty sets in production.
- **Root cause:** payouts API is NOT_FOUND officially, so items can only come
  from manual cabinet export — but nobody built the manual import path.
- **Proposed:** `POST /kaspi/payouts/{id}/items` (ACCOUNTANT) accepting item rows
  (`external_order_id`, amounts, `item_type`); service validates against
  `chk_kaspi_payout_items_*` constraints and links `order_id` via
  `uq_orders_ip_external` when resolvable (else `MISSING_ORDER` at reconcile
  time — by design). Plus `POST /kaspi/payouts/{id}/attach-operation`
  setting `operation_id` (the cash-received operation), guarded by the same-IP
  check used elsewhere.
- **Tests required:** item create → `reconcile_payout_full` → each of the 8
  match statuses; duplicate item across two payouts → `DUPLICATE`; totals
  mismatch → payout `DISCREPANCY`.
- **OWNER decision:** none for the mechanics. Policy question OQ-KASPI-002 —
  who is allowed to key in cabinet-export items (ACCOUNTANT sufficient, or
  separate role?) — can ship with ACCOUNTANT default.

### KASPI-003 — Payout commission never becomes an expense operation (P1, MEDIUM)

- **Evidence:** `kaspi_payouts.commission_amount` is stored; `EXPENSE_KASPI_FEE`
  operation type exists and ETL maps `"Комиссия"` to it — but no code posts a
  commission operation from a payout. The commission is visible in reports only
  as a payout column, never in P&L.
- **Proposed:** `post_payout_commission(session, payout_id)` service creating
  one `EXPENSE_KASPI_FEE` operation (`accrual_date = payout_date`, cash basis —
  consistent with the accrual foundation), idempotent via
  `import_fingerprint = "kaspi-commission:{payout_id}"`, linked back by setting
  `payout.operation_id` when the net receipt is posted together. Expose as
  `POST /kaspi/payouts/{id}/post-commission` (ACCOUNTANT), or a single
  "post payout to ledger" action creating both receipt and commission legs.
- **Tests required:** post twice → one commission operation (fingerprint);
  P&L includes commission in payout month; cash flow unaffected until receipt.
- **OWNER decision:** OQ-KASPI-003 — confirm that Kaspi commission is always a
  period expense at payout date (vs. accrued per order). Ships with payout-date
  default; owner can request per-order accrual later (needs order↔commission
  data that only the cabinet export provides).

### KASPI-004 — Kaspi Pay: correctly not integrated (P2, informational)

- **Evidence:** discovery CONFIRMS no public merchant API exists
  (PART2 §5). `KaspiPayClient` skeleton exists but is unwired — this is the
  correct state, not a gap to "fix" by invention.
- **Proposed:** keep frozen; document the supported path — Kaspi Pay money
  enters as bank-statement/manual operations (`SALE_KASPI_PAY`). If Kaspi ever
  publishes a merchant API, `KaspiPayClient` is the integration point.
- **Status:** MISSING-CAPABILITY (external). No owner action possible beyond
  "do not integrate via unofficial wrappers".

### KASPI-005 — Payout ↔ raw payload provenance not wired (P2, LOW)

- **Evidence:** `kaspi_payouts.raw_payload_id` exists, but `POST /kaspi/payouts`
  never accepts or sets it (`app/api/__init__.py::post_kaspi_payout`).
- **Proposed:** optional `raw_payload_id` on `KaspiPayoutCreate`, validated to
  belong to the same `ip_id`. One-line service change.
- **Tests required:** mismatched ip_id rejected (IDOR).

### KASPI-006 — ETL idempotency for Kaspi Excel: VERIFIED OK (no action)

- **Evidence:** Kaspi statement rows flow through `etl/import_excel.py` with
  `import_fingerprint` dedup (same path as P0-2 load tests: 100k rows, zero
  duplicates). No Kaspi-specific bypass exists (grep: zero "payout" references
  in `etl/`).
- **Status:** no gap.

### KASPI-007 — Returns/refunds: no API path, manual flow undocumented (P2, MEDIUM)

- **Evidence:** discovery: returns NOT_FOUND in Seller API; only `CANCELLED` +
  `orderEntryCancelOperation` are VERIFIED. `kaspi_payout_items.item_type`
  includes `REFUND`, and the reconciliation view handles `refund_amount` —
  but there is no documented procedure mapping a Kaspi return to ERP
  operations (revenue reversal + commission clawback per Договор п. 4.2).
- **Proposed:** document the manual refund runbook (cancel/return in cabinet →
  `REFUND` payout item → compensating operations; commission refund per
  Договор п. 4.2), without inventing API. Do NOT build a returns importer
  until Kaspi documents one.
- **OWNER decision:** OQ-KASPI-004 — confirm the accounting treatment of
  Kaspi returns (full revenue reversal in return month? commission reclaim
  as income?). This is business semantics; the runbook waits for it.

## Adapter architecture (banks beyond Kaspi)

Proposed interface — no invented contracts:

```
BankProvider (config: ip_id, credentials ref, source type)
  → ProviderAdapter (per bank: KaspiShopAdapter, KaspiManualFileAdapter, …)
  → NormalizedBankTransaction {external_id, date, amount, direction,
     counterparty_ref, purpose, raw_payload_id}
  → Reconciliation engine (existing reconcile_* services)
  → Financial Operation (existing postings)
```

- `KaspiManualFileAdapter` exists implicitly (ETL Excel path) — formalize it.
- `KaspiShopAdapter` = KASPI-001 (read-only orders).
- Halyk / Freedom adapters: MISSING-CAPABILITY until their official API
  contracts are verified per-bank (do not start without sources).
- `raw_kaspi_payloads` generalizes to `raw_bank_payloads` later — schema
  migration, not this task.
