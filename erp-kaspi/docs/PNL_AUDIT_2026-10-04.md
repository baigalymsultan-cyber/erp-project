# P&L Audit: operation_date vs accrual_date usage (2026-10-04)

**Scope**: Full repository search for `operation_date` in P&L vs Cash Flow contexts.
**Rule**: P&L must use `accrual_date` (strict: `IS NOT NULL`); Cash Flow must use `operation_date`.
**Method**: Read-only analysis. No code changed.

## Summary

**P&L violations found: 4** (places using `operation_date` for P&L calculations)
**P&L gaps found: 2** (places not setting `accrual_date`, causing P&L exclusion)
**Bug in uncommitted changes: 1** (transfers disappear from v_ip_financial_summary)

---

## P&L VIOLATIONS (must change to accrual_date)

### V1. app/api/__init__.py:581-587 — `/operations/daily` endpoint

```sql
SELECT operation_date::date AS day,
 SUM(CASE WHEN ot.kind = 'INCOME' THEN o.amount ELSE 0 END) AS income,
 SUM(CASE WHEN ot.kind = 'EXPENSE' THEN o.amount ELSE 0 END) AS expense
FROM operations o ...
WHERE o.operation_date BETWEEN :start AND :end
```

**Classification**: P&L VIOLATION
**Why**: Docstring says "daily POSTED-only income/expense series" — this is a P&L time series. Groups and filters by `operation_date` instead of `accrual_date`.
**Fix**: Change to `COALESCE` or strict `accrual_date` (match the `pnl()` service rule).

### V2. app/api/__init__.py:785,787 — `/operations/summary` endpoint

```python
stmt = stmt.where(Operation.operation_date >= period_start)
stmt = stmt.where(Operation.operation_date < period_end + timedelta(days=1))
```

**Classification**: P&L VIOLATION
**Why**: This endpoint aggregates `income`/`expense` by `OperationType.kind` (lines 816-820). It's a P&L summary filtered by cash date.
**Fix**: Filter by `accrual_date` for the income/expense aggregation.

### V3. app/services/__init__.py:457 — `pay_payroll()` operation creation

```python
operation = Operation(
    ...
    operation_date=payment_date,
    # accrual_date NOT SET → NULL
)
```

**Classification**: P&L VIOLATION
**Why**: Creates a `SALARY_PAYMENT` (kind=EXPENSE) operation. Under the strict `accrual_date IS NOT NULL` rule, this payment will NEVER hit P&L. But salary is a P&L expense! There is no separate accrual leg (`calculate_payroll()` posts zero operations).
**Fix**: Set `accrual_date=payment_date` (or the payroll period end date) when creating the payment operation. The payment IS the economic event for payroll.

### V4. Uncommitted: database/schema.sql v_ip_financial_summary (working tree)

Parent's uncommitted change adds `AND o.accrual_date IS NOT NULL` to the JOIN:
```sql
JOIN operations o ON o.ip_id = ip.id AND o.status = 'POSTED' AND o.accrual_date IS NOT NULL
```

**Classification**: P&L BUG
**Why**: Transfers have `accrual_date = NULL` by design (backfill policy). This JOIN excludes them from the ENTIRE view, including the `transfers_in`/`transfers_out` columns which are supposed to report transfers separately (§28).
**Fix**: Keep the JOIN inclusive; apply `accrual_date IS NOT NULL` only to the P&L sum filters, not to transfer reporting. Or use two CTEs.

## P&L GAPS (accrual_date not set → excluded from P&L)

### G1. app/services/__init__.py:588 — `add_operation()` generic creation

```python
op = Operation(
    ...
    operation_date=data.operation_date,
    # accrual_date NOT SET → NULL
)
```

**Classification**: P&L GAP
**Why**: Generic API for creating operations. Doesn't set `accrual_date`. Any INCOME/EXPENSE operation created via this API will have NULL accrual_date and be excluded from P&L under the strict rule.
**Fix**: API schema should accept `accrual_date`; default to `operation_date` for P&L types, NULL for transfers.

### G2. etl/import_excel.py:307 — ETL operation creation

```python
session.add(Operation(
    ...
    operation_date=operation_date,
    # accrual_date NOT SET → NULL
))
```

**Classification**: P&L GAP
**Why**: Imported operations get NULL accrual_date. Under strict rule, they won't hit P&L. Historical imports are the primary data source!
**Fix**: Set `accrual_date=operation_date` during import (matches backfill policy: imported data is historical, semantics = operation_date).

## INCONSISTENCY NOTE

The parent agent has uncommitted changes aligning `pnl()` service and `v_ip_financial_summary` view to strict `accrual_date IS NOT NULL` (no COALESCE fallback). This is stricter than the original migration 0015 design (which used COALESCE).

**Impact**: Any operation with NULL accrual_date is now invisible to P&L. This is correct for pure payments/settlements, but breaks:
1. `pay_payroll()` (V3 above) — salary payments won't hit P&L
2. `add_operation()` (G1 above) — API-created operations won't hit P&L
3. ETL imports (G2 above) — imported operations won't hit P&L
4. Transfers in the view (V4 above) — disappear entirely

**Recommendation**: Either (a) ensure ALL P&L-relevant creation paths set `accrual_date`, or (b) revert to COALESCE fallback for backward compatibility. Option (a) is cleaner but requires fixing V3, G1, G2.
