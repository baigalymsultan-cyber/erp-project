## 0. ВАЖНАЯ КОРРЕКТИРОВКА ПРЕДПОСЫЛКИ

В постановке задачи сказано: «официальные источники уже подтверждают: Halyk Open API для выписок, платежей и финансовых операций; Freedom API предоставляет statements с операциями, комиссиями и RRN».

**Проверка не подтверждает это.** Повторный поиск 2026-10-04 по официальным источникам:

- Публичного Halyk Open API **для выписок/платежей/выплат бизнеса не найдено** (статус из дока 2026-10-03 — NOT_FOUND — подтверждён повторно).
- Публичного Freedom API **не найдено вообще** (NOT_FOUND подтверждён повторно; statements/комиссии/RRN через API — MISSING-CAPABILITY).
- Что реально подтверждено: **Halyk ePay** (интернет-эквайринг, приём платежей картами) — это inbound acquiring, а не выписки.

Правило KASPI_OQ_003 действует и здесь: **не проектировать «Halyk API client для выписок» — такого публичного контракта нет.** Реалистичный путь — импорт выписок из файлов (MT940/Excel), как и сказано в доке 2026-10-03, §4.

## 3. Нормализованная схема банковской транзакции (proposal)

Выведена из стандарта SWIFT MT940 (ISO 15022 — публичный стандарт; Halyk официально экспортирует MT940) и KZ-практики (код назначения платежа КНП — обязателен для KZ-учёта). Это **внутренняя схема ERP**, не банковский контракт.

```yaml
# NormalizedBankTransaction — то, что обязан выдать каждый ProviderAdapter
provider_code:      str    # HALYK | FREEDOM | EPAY | KASPI_SHOP | KASPI_PAY | MANUAL
provider_account:   str    # IBAN / номер счёта в банке (как в выписке)
ip_account_id:      int    # FK -> accounts.id (сопоставлен при импорте, не из банка)
value_date:         date   # дата валютирования (MT940 :61: value date)
entry_date:        date    # дата проводки банком (может отличаться)
amount:            Decimal  # всегда положительная
currency:          str     # KZT | USD | EUR | ...
direction:         str     # IN | OUT (дебет/кредит с точки зрения счёта)
document_number:   str     # номер платёжного документа (MT940 :61: reference)
bank_reference:    str     # уникальный референс банка (для дедупликации)
counterparty_name: str | None
counterparty_iin:  str | None   # ИИН/БИН (12 цифр), если есть в выписке
counterparty_bik:  str | None   # БИК банка контрагента
counterparty_account: str | None # счёт контрагента
payment_purpose:   str | None   # назначение платежа (MT940 :86:)
knp_code:          str | None   # код назначения платежа КНП (KZ-специфика)
commission:        Decimal | None  # комиссия банка отдельной строкой, если выделена
balance_after:     Decimal | None  # остаток после операции (для сверки)
raw_line:          str     # исходная строка выписки (provenance, неизменяемая)
source_file_hash:  str     # SHA-256 файла выписки (дедупликация на уровне файла)
line_no:           int     # номер строки в файле (аудит)
```

**Дедупликация** (аналог `import_fingerprint`): `SHA-256(provider_code | provider_account | value_date | amount | direction | document_number | bank_reference)`. Повторный импорт того же файла → все строки `duplicates`, ноль новых операций (семантика P0-2).

## 4. Дизайн адаптера

```
BankProvider (enum: HALYK, FREEDOM, EPAY, KASPI_*)
      │
      ▼
ProviderAdapter (abstract)
  ├── MT940Parser          — Halyk Onlinebank (SWIFT MT940)
  ├── ExcelStatementParser — Freedom Business / ручная выгрузка (column-map как etl/column_map.example.yaml)
  └── EPayWebhookAdapter   — Halyk ePay webhook → "order paid" event (будущее, checkout)
      │
      ▼  list[NormalizedBankTransaction]
StatementImportService
  ├── validate (схема § выше, §94: неизвестное — ошибка, не догадка)
  ├── deduplicate (fingerprint, батчинг по 1000 — урок P0-2)
  ├── match → operations (reconciliation engine, §5)
  └── persist: raw_bank_statements (provenance) + bank_statement_lines (staging)
      │
      ▼
Reconciliation → Financial Operation (operations, POSTED/DRAFT по политике)
```

**Принципы:**
- Формат-ориентированный импорт, не банк-ориентированный: новый банк = новый `ProviderAdapter`, ядро не меняется.
- Никаких выдуманных API-клиентов для выписок (MC-1..MC-3).
- `raw_bank_statements` хранит исходный файл целиком (аудит, повторная обработка) — аналог `raw_kaspi_payloads`.
- Статус строк сверки: `UNMATCHED` → `SUGGESTED` (авто-совпадение) → `CONFIRMED` (ручное) / `IGNORED`. Авто-проводка в ledger только для точных совпадений по политике (см. OD-BANK-3).

## 5. Reconciliation engine (требования)

Минимальный matcher v1 (детерминированный, без ML):

1. **Точное совпадение:** `amount` + `value_date ±1 день` + `direction` + (`counterparty_iin` или нормализованное `counterparty_name`) → `SUGGESTED`.
2. **Комиссии:** строки с `knp_code` комиссионных кодов или маркером банка → предлагаются как `EXPENSE_BANK_FEE` (тип существует? проверить `operation_types`; если нет — gap).
3. **Несовпадения:** `UNMATCHED`, ручное сопоставление в UI (тот же UX-паттерн, что `v_kaspi_reconciliation`).
4. **Контроль остатков:** `balance_after` последней строки должен сходиться с предыдущей + оборот; расхождение → `FAILED` с явной ошибкой (не молча).

## 6. Gaps в текущем ERP

| ID | Gap | Severity | Evidence | Что есть сейчас |
|---|---|---|---|---|
| G-BANK-1 | У `accounts` нет идентификатора банка | P1 | `database/schema.sql:1095` — только `name`, `type='BANK'`; два счёта в Halyk неразличимы программно | `accounts.type` уже включает `'BANK'` ✓ |
| G-BANK-2 | Нет таблицы `raw_bank_statements` | P1 | существует только `raw_kaspi_payloads` (Kaspi-специфичная, `api_type IN ('SHOP','PAY')`) | provenance-инфраструктура есть, нужна generic-таблица |
| G-BANK-3 | Нет staging-таблицы строк выписки | P1 | нет аналога для банковских строк | `import_batches.source_type` уже включает `'BANK'` ✓ |
| G-BANK-4 | Нет MT940-парсера | P1 | `etl/` содержит только `import_excel.py` (Kaspi Excel) | P0-2 chunking/fingerprint переиспользуемы |
| G-BANK-5 | Нет reconciliation для банков | P1 | `v_kaspi_reconciliation` — только Kaspi | паттерн сверки есть, нужен generic |
| G-BANK-6 | Нет webhook-приёмника ePay | P2 | — | только будущее (checkout «заказ оплачен») |
| G-BANK-7 | `EXPENSE_BANK_FEE` — проверить наличие типа | P2 | — | проверить `operation_types` перед реализацией §5.2 |

**Что уже готово (не gaps):** `import_batches` с `source_type='BANK'`; `accounts.type='BANK'`; fingerprint-дедупликация с батчингом (P0-2); chunked import с resume; `error_details` JSONB для строк ошибок.

1. `raw_bank_statements` + `bank_statement_lines` (миграция, staging, provenance) — **A**.
2. `NormalizedBankTransaction` (dataclass/Pydantic) + `ProviderAdapter` ABC — **A**.
3. `MT940Parser` (SWIFT MT940 — публичный стандарт, Halyk официально экспортирует) — **A**.
4. `ExcelStatementParser` на базе существующего column-map механизма ETL — **A**.
5. `bank_code` на `accounts` (миграция, nullable, не ломает существующее) — **A**.

## 8. OWNER decisions (категория C — только настоящий бизнес-выбор)

### OD-BANK-1: Приоритет банков для file-import
- **Вопрос:** с какого банка начинать импорт выписок?
- **A:** Halyk первым (формат MT940 подтверждён официально — наименьший риск).
- **B:** Freedom первым (если у owner уже есть выгрузка и пример файла).
- **C:** Оба параллельно (дольше, но симметрично).
- **Что продолжается без решения:** G-BANK-1..5 (вся инфраструктура банк-нейтральна).

### OD-BANK-2: ePay acquiring в scope?
- **Вопрос:** нужен ли приём онлайн-платежей через Halyk ePay (виджет + webhook «заказ оплачен»)?
- **A:** Да (требует договор с Halyk, TerminalID/ClientID/ClientSecret — REQUIRES_REAL_ACCOUNT).
- **B:** Нет, только выписки/сверка.
- **Что продолжается без решения:** весь file-import тракт (§4 без EPayWebhookAdapter).

### OD-BANK-3: Политика авто-сопоставления при сверке
- **Вопрос:** какие совпадения проводить в ledger автоматически?
- **A:** Только точные (сумма + дата ±1 + контрагент) → остальные вручную.
- **B:** A + нечёткие по назначению платежа с ручным подтверждением.
- **C:** Всё вручную (максимум контроля, минимум автоматизации).
- **Что продолжается без решения:** движок с configurable политикой, default = A (самый безопасный).
